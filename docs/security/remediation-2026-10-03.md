# Security remediation and verification

Baseline: `dfbeb6e15cf2be6ff7cd3d00ad980ffedcdd6ab5`.

The user authorized additional verification, remediation and a pull request. Verification uses synthetic local Firebase identities, disposable libSQL databases and the guarded QA runner. No production data, provider credentials, live notifications or provider configuration were changed. The earlier source audit retained candidates as `needs_validation`; this document records the narrower evidence obtained during remediation.

## Additional corrections

Native push teardown retires the registration, removes listeners and delivered notifications, attempts token deletion and unregisters before Firebase identity teardown. A generation and UID check reject delayed callbacks from an earlier registration. Best-effort native cleanup has a timeout so offline push persistence cannot indefinitely prevent authentication teardown. A runnable adapter regression covers registration for one user, logout, registration for another and a delayed old callback. Actual FCM delivery, already queued operating-system notifications and device behavior require separate evidence.

The Cloudflare deploy job selects the existing `Production` or `Preview` environment. Its preview step references only `CLOUDFLARE_PREVIEW_API_TOKEN`; an absent token skips publication without emitting a deployment URL or claiming successful publication. Android publication requires all signing inputs, restrictive temporary file permissions and `assembleRelease`; it uploads only the release artifact. Release signing was not executed locally.

## Dependency advisories

Compatible security updates cover Next.js and its lint plugin, DOMPurify, js-yaml, undici, brace-expansion, gRPC and the Functions-only fast-uri dependency. Root and Functions lockfiles are updated. The existing OpenNext response adapter patch remains active.

Registry audit results moved from 27 root advisories (1 critical, 12 high, 8 moderate, 6 low) to the single high advisory mitigated below. The separate Functions audit moved from 6 advisories (3 high, 2 moderate, 1 low) to zero. These are dependency-graph audit results, not counts of independently exploitable application vulnerabilities.

The registry still reports [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) for `braces@3.0.3`, a development-tool dependency without a published corrected version at verification time. A pnpm patch limits parser nesting and recursive compile, expand and stringify AST traversal. The regression rejects deeply nested string and AST inputs and preserves ordinary glob expansion. The package version remains affected in registry metadata; this is a tested local mitigation, not a claim of a clean root registry audit. Remove the patch only after reviewing an upstream fix and rerunning its regression. This patch addresses the cited stack-exhaustion issue, not arbitrary expansion cardinality or other undiscovered defects.

## External completion requirements

Read-only GitHub inspection found `main` protected, but `Production`, `Preview` and `Staging` have empty environment protection rules and no deployment branch policies. Cloudflare production and Android signing secret names are present at repository scope; `Preview` has no secrets and `Production` currently lists only the Firebase service account secret. Secret values were never read or printed.

Before considering release authority isolated, move production deployment and signing credentials out of repository scope into the protected `Production` environment. Restrict that environment to `main` and approved release tags, and configure the required release approval policy. Supply a separate preview token through `Preview`, scoped only to the preview Worker and its necessary resources. Do not duplicate the production token under a new name. Cloudflare supports individual Worker permission policies in its [Workers authorization documentation](https://developers.cloudflare.com/workers/authorization/workers/); an actual token's policy was not inspected. GitHub protection and secret scope are provider configuration, not properties guaranteed by the workflow diff. See [GitHub environment controls](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments).

Deploy the reviewed rules and Functions through the existing staging and production release procedure. Verify deployed fingerprints and section/period/enrollment projection parity, real Worker private HTML and RSC cache rejection, institutional identity provider admission, App Check rollout, final APK signing and native logout/push behavior using dedicated staging identities. Local emulator and simulated-provider checks do not establish these results.

Existing observations concerning notification fanout and replay handling, storage upload cleanup under provider failure, floating workflow action references, CSP inline scripts, backup/restore and monitoring remain hardening or external assurance work. This remediation does not promote those observations to reproduced vulnerabilities or mark them safe. No claim of complete production security is made.
